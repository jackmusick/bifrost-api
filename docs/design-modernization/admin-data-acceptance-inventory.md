# Admin Data Acceptance Inventory

Scope: Config, Files, Tables/records, Knowledge, Organizations, Users, Roles, Solutions, Diagnostics, Audit, ROI Reports and Usage Reports. This is an inventory of source actions and existing evidence only. It does not add new acceptance claims, run tests, or mark the journey ledger complete. The new `config-acceptance.admin.spec.ts` and `role-lifecycle-acceptance.admin.spec.ts` passed targeted iteration validation; see `ui-acceptance-plan.md` for commands. They do not cover every action on either page.

Evidence strength labels:

- **Real e2e**: Playwright drives the real UI and real Bifrost API resources.
- **Synthetic route acceptance**: Playwright/browser route evidence with intercepted API responses; strong for UI state, recovery, layout, and request contracts, but not backend authorization or persistence.
- **Component/unit**: Vitest or unit evidence for component contracts.
- **Structural smoke**: Browser loads or sees affordances, but does not prove the full workflow.

## Redundant or Non-Proving Browser Checks

- The prior `permissions.user.spec.ts` had heading-only checks for org-user access to Home, History, Forms, and generic navigation absence. Those are now intentionally replaced by one deterministic `/config` denied-route and recovery journey. Assigned/forbidden form behavior is already covered by `forms.user.spec.ts`; execution behavior/history is covered by execution specs.
- The placeholder “own organization data only” test proved no data boundary because it made no specific cross-org assertion.
- Structural smoke specs such as `solutions.admin.spec.ts` and parts of `solution-lifecycle.admin.spec.ts` are useful as affordance checks, but they should not be counted as lifecycle acceptance for install/update/delete flows.

## Cross-Org / Authorization Evidence

Straightforward browser-side route denial exists for several admin routes in the route review docs, usually via synthetic authenticated non-admin fixtures that assert no protected data reads. That is frontend route-boundary evidence only.

Real cross-org API authorization evidence should be audited separately from this document. Do not infer it from hidden navigation, from synthetic browser fixtures, or from the placeholder org-user tests removed from `permissions.user.spec.ts`.
